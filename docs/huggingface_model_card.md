# NanoMind-SLM-60M

NanoMind-SLM is an educational, decoder-only Transformer trained from random
initialization on Python source code. It demonstrates a complete
small-language-model pipeline: bounded streaming data preparation, filtering,
byte-level BPE tokenization, fixed-length packing, a custom PyTorch model, training,
checkpointing, greedy inference, and finite evaluation.

The released model has **18,808,704 parameters**. “60M” refers to the roughly
62.5 million packed training tokens, not the parameter count. This is a learning
and portfolio project, not a production coding assistant.

## Model details

| Property | Value |
|---|---:|
| Parameters | 18,808,704 |
| Architecture | Llama-style decoder-only Transformer |
| Components | GQA, RoPE, RMSNorm, SwiGLU, tied embeddings |
| Layers | 10 |
| Hidden width | 384 |
| Attention heads | 6 query / 2 key-value |
| Feed-forward width | 1,024 |
| Vocabulary | 8,000-token byte-level BPE |
| Context length | 256 tokens |
| Reported packed training corpus | 62,531,072 tokens |
| Checkpoint size | 75,265,675 bytes |
| Framework | PyTorch |

## Training data and provenance

The data pipeline streams `codeparrot/codeparrot-clean` at revision
`35a59fb025bc0a102f7d96eac09d145b896d487b`. The released quality branch uses
license, content-length, autogenerated-metadata, and longest-line filters. It
does **not** parse the source with `ast.parse`, prove functional correctness, or
detect every form of low-quality or vendored code.

The published corpus format separated files with blank lines, while the shard
builder also treated blank lines inside a file as boundaries. This could insert
`<eos>` within a source file. The behavior is documented and retained for
checkpoint provenance; changing it would require a versioned pipeline and a
newly trained model.

## Evaluation

### Historical release measurements

| Measurement | Historical value |
|---|---:|
| Packed validation corpus | 6,277,632 tokens |
| Validation loss | 2.156258 |
| Perplexity | 8.638752 |
| Evaluated batches | 500 |
| Evaluated input tokens | 1,024,000 |
| Saved outputs accepted by `ast.parse` | 5/10 |
| Same saved outputs accepted by `compile(..., "exec")` | 5/10 |

The metric files are preserved, but the exact release-time validation corpus,
shard hashes, and evaluation command were not retained. The historical 2.156258
loss therefore has **not** been freshly reproduced.

### Pinned rebuild measurement

On 2026-09-20, the current pinned pipeline rebuilt a held-out quality corpus and
packed it with the released tokenizer. The rebuild produced 6,289,664 validation
tokens, which differs from the historical 6,277,632 tokens. A new CPU evaluation
(Python 3.14.0, PyTorch 2.13.0+cpu, batch size 8, first 500 finite batches)
measured loss **2.159504** and perplexity **8.666837** over 4,000 sequences,
1,024,000 input tokens, and 1,020,000 next-token predictions. This is a separate
measurement on rebuilt inputs, not a reproduction or replacement of the
historical result.

The rebuilt corpus SHA-256 is
`66b125c8bfafe0340365d618091d045138178fc4643ebe9a1e320e3ea04c9dc1`;
the released tokenizer SHA-256 is
`412483f17f31fcfe6af8a8b5ccfda5777177222c0d612c5e253aa61bf7b3c75e`.
The repository's dated evaluation report records the remaining configuration
and artifact hashes.

### Generated-code checks

| Greedy inference policy | AST-parseable | Compile-valid |
|---|---:|---:|
| Current default, with `<bos>` | 8/10 | 7/10 |
| A/B variant, without `<bos>` | 6/10 | 4/10 |

`ast.parse` checks whether Python can construct an abstract syntax tree.
`compile(source, "<generated>", "exec")` applies additional compiler checks,
including rejection of duplicate function arguments. The evaluation never
executes generated code. Neither measurement establishes that a completion is
correct, useful, safe, or equivalent to a functional benchmark such as pass@1.

The baseline, earlier-quality, and final-quality runs used separately trained
tokenizers, and the saved evidence does not establish equal data or optimizer
budgets. Their scores are therefore historical observations, not a controlled
proof that filtering caused an improvement.

## Intended use

- Learning how a small decoder-only language model is built end to end
- Inspecting a custom PyTorch architecture and data pipeline
- Reproducing deterministic greedy generation from the released checkpoint
- Studying evaluation and provenance limitations in a small project

## Limitations

- The model frequently produces incomplete, repetitive, or logically incorrect
  Python.
- AST parsing and compilation do not measure functional correctness.
- The context window is only 256 tokens.
- The default demo prepends `<bos>`, although packed training sequences did not.
- The architecture is custom PyTorch code and is not directly compatible with
  the standard Transformers `AutoModel` interface.
- No MBPP, HumanEval, pass@1, security, or controlled filtering-only benchmark
  has been completed.
- No license is currently declared for the repository or model. Do not assume
  permission for open-source reuse until the author selects one.

Do not use this model for production or security-sensitive code without human
review and independent testing.
