# Data pipeline and provenance

This document describes the data path that produced the published
NanoMind-SLM checkpoint and separates measured facts from the project's early
experimental plan.

## Source and safety constraints

- Dataset: `codeparrot/codeparrot-clean`
- Revision: `35a59fb025bc0a102f7d96eac09d145b896d487b`
- Split: `train`
- Access: Hugging Face Datasets with `streaming=True`
- Split unit: source repository, assigned deterministically with SHA-256
- Duplicate identity: the dataset-provided exact content hash
- Raw source files: not committed

The builders are bounded by record and character limits and do not load the
complete dataset into memory. Train and validation assignment happens at the
repository level to reduce same-repository leakage.

## Implemented filtering

Both corpus branches require non-empty string content and one of these detected
licenses: Apache-2.0, MIT, BSD-2-Clause, or BSD-3-Clause.

The quality branch additionally requires:

- 100–100,000 characters;
- no `autogenerated=True` metadata flag; and
- no line longer than 1,000 characters.

These checks are metadata and length filters. They do not parse Python syntax,
detect vendored code beyond the available metadata, or prove functional
quality. In particular, `src/nanomind_slm/data/filtering.py` does not use
`ast.parse`, so the published dataset is not AST-validated.

## Bounded audit evidence

The historical 2026-07-10 audit inspected the first 1,000 streamed records
without printing or storing their source. Its three audit scripts called
`load_dataset` without a `revision` argument, so these are **unpinned historical
observations**, not evidence tied to a specific dataset revision:

| Observation | Count |
|---|---:|
| Records inspected | 1,000 |
| Baseline accepted | 599 |
| Quality accepted | 595 |
| License-policy rejections | 401 |
| Additional oversized-file rejections | 4 |

Declared file sizes ranged from 1,028 to 456,237 characters, with a mean of
10,641.16.

On 2026-09-20, `scripts/audit_dataset.py` successfully repeated the audit with
the configured revision
`35a59fb025bc0a102f7d96eac09d145b896d487b`. That pinned run inspected 1,000
records, accepted 599 with the baseline filter and 595 with the quality filter,
and reproduced the same size summary and rejection counts shown above. This is
new revision-pinned evidence; it does not retroactively make the 2026-07-10 run
pinned.

Both runs describe the first 1,000 records returned by their respective
streams, not a random sample or a dataset-wide estimate. The consolidated
script is bounded, requires streaming mode, checks the expected schema, and
does not print or store source code.

## Tokenizers and packing

The project trained separate 8,000-entry byte-level BPE tokenizers for the
baseline and quality corpora. Special IDs are `<pad>=0`, `<unk>=1`, `<bos>=2`,
and `<eos>=3` in the released tokenizer.

Training text was encoded with `add_special_tokens=False`; packing inserted an
`<eos>` token at each document boundary and emitted complete 256-token blocks.
`<bos>` was therefore defined by the tokenizer but was not added to training
sequences.

### Published boundary-format limitation

`build_tokenizer_corpora.py` wrote complete code files separated by blank lines.
`build_tokenized_data.py` interpreted every blank line—including a blank line
inside a Python file—as a document boundary. As a result, packing could insert
`<eos>` inside a file and treat indented fragments as separate documents.

The repository retains that behavior because changing it would change the
training corpus. A corrected pipeline should use an unambiguous record format
(for example, length-delimited records or JSON Lines), receive a new data-format
version, and produce a separately named checkpoint after retraining and
reevaluation. The published checkpoint must not be described as having used the
corrected semantics.

New shard manifests include exact tokenizer, corpus, and per-shard SHA-256
values so an evaluation's inputs can be identified and incompatible token IDs
can be rejected. Older manifests without a tokenizer hash have unverified
tokenizer provenance and require explicit acknowledgement in the evaluator.

## Experiment interpretation

The baseline and quality branches are useful evidence of pipeline exploration,
but they are not a controlled filtering-only experiment: they used separately
trained tokenizers, and the saved comparisons do not establish equal data and
optimizer budgets. The historical syntax observations (1/10 baseline, 0/10
earlier quality, 5/10 final quality) must not be used to claim that filtering
alone caused an improvement.

For the final release, 62,531,072 is the reported size of the packed training
corpus. The nominal full-batch schedule—7,634 steps × batch 4 × gradient
accumulation 8 × context 256—corresponds to 62,537,728 input positions. Those
are related but distinct measurements. Without the final manifest and sampler
record, the exact number of positions consumed by the optimizer cannot be
reconstructed and should not be asserted as the corpus size.

## Reproduction status

The released model configuration, tokenizer, checkpoint, and metric JSON are
available on Hugging Face. The exact release-time validation corpus, shard
hashes, and evaluation command were not committed. The smaller local development
shards were produced with an earlier tokenizer and are not compatible evaluation
data for the release checkpoint.

On 2026-09-20, the current pinned builder scanned 100,000 records and rebuilt a
quality-validation corpus containing 2,295 accepted records and 19,999,789
source characters. Its SHA-256 is
`66b125c8bfafe0340365d618091d045138178fc4643ebe9a1e320e3ea04c9dc1`.
Packing that corpus with the released tokenizer (SHA-256
`412483f17f31fcfe6af8a8b5ccfda5777177222c0d612c5e253aa61bf7b3c75e`)
produced 24,569 complete 256-token blocks, or 6,289,664 tokens. That differs
from the historical 6,277,632-token validation corpus by 12,032 tokens, so it
cannot establish that the original evaluation inputs were recovered.

A new finite CPU evaluation on the rebuilt shards measured loss 2.159504 and
perplexity 8.666837 over 500 batches, 4,000 sequences, and 1,020,000 predicted
tokens. It is recorded separately in
`reports/pinned_rebuild_evaluation_bos_2026-09-20.json`, together with the data
configuration, corpus, manifest, tokenizer, checkpoint, and per-shard hashes.
It is a new measurement, not a reproduction or replacement of the unchanged
historical 2.156258 loss.
